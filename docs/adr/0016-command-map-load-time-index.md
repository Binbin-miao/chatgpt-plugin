# 指令地图的归一化在加载期做，热路径只读预计算字段

状态：已采纳（2026-11-04）。需求与实测数据见 `.scratch/指令地图审查/第二轮_对标与性能_20261104.md`。

2026-11-04 用真实的 31 份地图（1411 条指令）跑了一遍基准：一次 `searchEntries` 要 **7.1ms**，
`loadEntries()` 缓存命中还要 **0.9ms**——后者全是 1 次 `readdirSync` + 31 次 `statSync`，
前者大头是每条消息对上千条重复做 `NFKC + 正则去噪 + 插件名括注裁剪`。这些都是同步 IO / 同步计算，
直接堵在事件循环上。

外部对标 AstrBot（`AstrBotDevs/AstrBot`，45.9k stars）：它的 `CommandDescriptor` 在注册期就带好
权限、别名、冲突标记，`CommandFilter` 构造时缓存完整指令名列表，`llm_tools` 是模块级单例。
结论一致：**能预建的东西不要在热路径重算**。

于是两条改动：

1. `flattenEntries()` 里给每条条目预计算 `_norm`（归一化写法/关键词/描述/场景、插件名去括注与去后缀、
   key 与分类的小写）与 `_lower`（字面小写）。`scoreEntries` / `isSamePlugin` / `commandWeight` 只读这些
   字段；测试里手工构造、没有预计算字段的条目走一个等价的现场计算兜底，保证行为不漂移。
2. 条目表缓存改为「写侧置空 + 目录指纹 + 低频复核」：`writeEntry` / `pruneUninstalled` 成功后立即
   `entriesCache = null`；`loadEntries()` 每次只 `statSync` 地图目录本身（1 次 IO）比对 mtime，
   10 秒才做一次完整的 31 份文件签名复核。

## 考虑过的替代方案

- **预建 `Map<归一化写法, entry[]>` 精确索引，查询先 O(1) 短路**：原型实测 8629 个键只要 7ms 就能建好，
  真实写法覆盖 1411/1411，精确查询降到接近 0。**没有采用**，因为 `scoreEntries` 不只要精确命中，还要
  给「写法包含」「关键词包含」「模糊兜底」打分；短路掉全表会让这些长尾命中消失，结果不再等价。
  预计算归一化字段已经把 7.1ms 降到 0.9ms（7.9 倍），性价比更高且零行为风险。
- **完全去掉签名，只靠写侧置空**：测试与运维直接改 `entry.json` 时永远看不到。保留目录指纹与 10 秒
  复核，换取「手工改文件最多 10 秒生效」。
- **用 `fs.watch` 监听目录变化**：跨平台行为不稳、热重载时容易重复注册，不值得为这 0.9ms 引入。
- **缓存 `buildPromptAddon` 的结果**：实测它只要 0.043ms，做了没有可感知收益，不做。
- **优化 `resolveCommand` 的 `dedupeByCommand` 与 `suggestEntries` 的 `commonRun`**：分别 1.6ms / 4.1ms，
  确有空间，但改动会碰匹配语义。本轮按「只做低风险两项」的范围先不动，留到票 09 评估。

## 已知约束

- 预计算字段让每条条目多了两个对象，1411 条约增加几 MB 常驻内存；换的是每条消息 8ms 的同步开销，划算。
- 归一化口径必须与 `NOISE_RE` / `FILLERS` 保持在同一个文件里；将来改去噪规则，缓存会随地图重新加载自动重算。
- 手工改写单份 `entry.json`（不增删子目录）最多 10 秒后才生效。想立刻生效可发 `#指令地图更新`。
- 若将来地图数量涨到几百份，`statSync` 目录 1 次仍是常数，但 `flattenEntries()` 的一次性成本会线性增长——
  那时再考虑把预计算索引也落盘。
